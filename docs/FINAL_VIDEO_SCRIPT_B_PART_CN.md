# ASR-Mobile 项目视频文稿：B 负责部分

## 0. 开场

大家好，我在 ASR-Mobile 项目中主要负责 Android 端部署、benchmark 系统完善和真机实验分析。

我的工作重点不是生成模型本身，而是回答一个更偏工程部署的问题：

```text
这些 ASR 模型放到 Android 手机上之后，能不能加载，能不能离线运行，运行速度如何，是否适合真实移动端部署？
```

所以我这一部分主要围绕 Android App、真机测试、benchmark 指标、CSV 数据导出和最终部署结论展开。

## 1. 我负责的项目目标

整个 ASR-Mobile 项目的目标是在 Android 手机上实现离线语音识别。

从我负责的系统侧来看，完整流程是：

```text
Android UI -> 手机录音 -> WAV 文件 -> Kotlin WhisperEngine -> JNI -> whisper.cpp -> 转写文本和性能指标
```

我的任务是把这个流程跑通，并且让它可以被量化评估。

也就是说，项目不只是能识别一句话，还要能回答：

- 模型加载用了多久？
- 推理用了多久？
- RTF 是多少？
- 是否快于实时？
- 模型大小是多少？
- 手机端内存变化如何？
- 转写结果是否还能接受？

这些指标决定了模型是否真的适合 Android 离线部署。

## 2. Android App 功能完善

在 Android 端，我主要完善了 App 的实验能力。

首先是录音流程。App 可以在手机上录制 10 秒音频，并保存为本地 `latest.wav` 文件。这样后续所有模型都可以使用同一段录音测试，保证 benchmark 对比更加公平。

其次是模型加载流程。App 支持加载内置模型，也支持加载外部 `.bin` 模型文件。模型加载时会记录加载时间，这个指标很重要，因为移动端体验不只看推理速度，也看用户等待模型初始化的时间。

然后是转写流程。App 会通过 Kotlin 的 WhisperEngine 调用 JNI，再由底层 whisper.cpp 执行本地推理。整个过程不需要云端服务，符合离线 ASR 的项目目标。

最后是 benchmark 流程。我把 benchmark 从一次简单测试扩展成了可记录、可导出、可复现的实验流程。

## 3. Benchmark 指标设计

我在 benchmark 中记录了这些字段：

- 设备型号
- Android 版本
- CPU ABI
- 模型名称
- 量化等级
- 音频语言
- 模型路径
- 模型大小
- 音频长度
- 模型加载时间
- 推理时间
- RTF
- Java heap 变化
- native heap 变化
- 转写文本
- 质量评分和备注

其中最核心的是 RTF，也就是 real-time factor。

RTF 的计算方式是：

```text
RTF = 推理时间 / 音频时长
```

如果 RTF 小于 1，说明模型推理速度快于实时，比较适合交互式语音识别。

如果 RTF 大于 1，说明转写速度比音频播放还慢，移动端体验会比较差。

所以在我的实验分析里，RTF 是判断模型是否适合手机部署的关键指标。

## 4. UI 和可视化进度优化

为了让实验过程更清楚，我也优化了 Android UI。

App 现在有：

- 状态提示区域
- 进度条
- 当前进度文字
- 实验摘要面板
- 音频语言输入框
- benchmark 结果显示区域

实验摘要会显示当前模型、量化等级、模型大小、录音文件、加载时间和语言。

这样录视频或演示时，可以直观看到当前实验处于哪个阶段，避免只看日志或命令行。

## 5. 自动化测试支持

由于我们要比较多个模型，如果完全手动选择模型、加载模型、运行 benchmark，会非常慢，也容易出错。

所以我增加了 ADB 自动化支持。

现在可以通过命令直接指定：

- 模型路径
- 模型名称
- 音频语言
- 是否自动加载
- 是否加载后自动 benchmark

也就是说，手机 App 可以被脚本驱动，自动完成多模型测试。

我还准备了几个脚本：

```text
sync_day4_models_to_device.sh
run_day4_benchmark_matrix.sh
summarize_day4_benchmarks.py
generate_day4_report_assets.py
```

第一个脚本负责把模型同步到手机 App 私有目录。

第二个脚本负责批量运行模型 benchmark。

第三个脚本负责汇总 CSV，计算每个模型的平均推理时间和平均 RTF。

第四个脚本负责生成报告用图表和质量分析表。

这些脚本让实验过程更加可复现，也减少了手动抄写数据的错误。

## 6. 真机测试环境

我使用的测试设备是华为手机：

```text
Device: HUAWEI HBN-AL10
Android: 12
ABI: arm64-v8a
```

正式测试音频是一段 10 秒中文录音，内容是：

```text
这是 ASR Mobile 项目的第四天正式测试。我们正在比较不同量化模型在华为手机上的离线语音识别速度和识别质量。
```

每个模型重复运行 3 次，然后取平均推理时间和平均 RTF。

这样做可以减少单次运行受到系统负载影响带来的偶然误差。

## 7. Android 加载验证

在正式 benchmark 之前，我先做了模型加载验证。

这一步的目的不是比较速度，而是确认模型文件真的能被 Android App 加载。

我验证了 tiny 和 base 系列的多个量化模型，包括 Q8、Q5、Q4。

结果显示，这些模型放在 App 私有目录下可以成功加载。

这个发现也很重要：模型放在普通外部目录时，可能因为 Android 权限和路径问题加载失败；而放在 App 私有目录下更稳定。

所以后续正式实验都使用：

```text
/data/user/0/com.example.asrmobile/files/models/
```

作为模型路径。

## 8. 正式 Benchmark 结果

正式中文 benchmark 中，我重点测试了几个核心模型。

结果如下：

| 模型 | 平均推理时间 | 平均 RTF | 结果 |
|---|---:|---:|---|
| `ggml-tiny.bin` | 8226.67 ms | 0.822 | 成功，快于实时 |
| `ggml-tiny-q8_0.bin` | 40064.67 ms | 4.006 | 成功，但明显变慢 |
| `ggml-tiny-q5_1.bin` | 108814.67 ms | 10.882 | 成功，但非常慢 |
| `ggml-base-q8_0.bin` | 111234.33 ms | 11.123 | 成功，但不适合实时 |
| `ggml-base-q5_1.bin` | 超时 | 超时 | benchmark 超时 |

从我的 Android 实测角度看，最重要的结论是：

```text
ggml-tiny.bin 是当前最适合 Android 端部署的模型。
```

它的平均 RTF 是 0.822，是这组正式测试中唯一快于实时的模型。

## 9. 对量化结果的系统侧分析

从模型大小看，量化确实让模型变小了。

比如 tiny Q8 和 tiny Q5 都明显小于原始 tiny baseline。

但是从 Android 真机推理速度看，量化模型并没有变快，反而明显变慢。

这说明一个重要问题：

```text
模型压缩不等于移动端推理一定加速。
```

实际速度还取决于：

- whisper.cpp 对量化格式的支持
- Android native 后端实现
- ARM CPU 对低精度计算的支持
- 线程调度
- 内存访问开销
- 手机当前运行状态

所以我的部分最终证明了：移动端部署必须做真机 benchmark，不能只根据模型大小做判断。

## 10. 识别质量观察

从转写结果看，各个成功模型都能识别出大致语义，但都有一些错误。

比如 `ASR Mobile` 有时会被识别成相近但错误的内容，`语音识别` 也会出现错字。

我还生成了一个简单的质量分析表，用字符级编辑距离估算识别质量。

这个分析不是严格标准化的 CER/WER 评测，但可以作为报告中的辅助观察。

整体来看，tiny baseline 的识别质量可用，同时速度最好，所以它是最适合当前系统部署的选择。

## 11. 我的最终结论

我负责的 Android 系统实验最终得出三个结论。

第一，ASR-Mobile 可以在 Android 手机上完成本地离线语音识别。

第二，benchmark 系统可以记录模型大小、加载时间、推理时间、RTF、内存变化和识别文本，并导出 CSV 用于报告分析。

第三，在当前华为手机和 whisper.cpp Android 后端上，`ggml-tiny.bin` 是最实用的模型。量化模型虽然更小，但实际推理更慢，不适合作为当前默认部署模型。

所以最终推荐：

```text
ggml-tiny.bin
```

## 12. 我这部分的价值

我这部分工作的价值在于，把模型侧的压缩结果真正放到了 Android 手机上验证。

如果只看模型大小，可能会认为 Q8 或 Q5 更好，因为它们更小。

但是通过真机 benchmark，我们发现它们在当前系统中明显更慢。

因此，我的工作为项目提供了真实部署结论：

```text
移动端 ASR 优化不能只看压缩率，必须同时看真实设备上的速度、RTF 和识别可用性。
```

这也是整个 ASR-Mobile 项目的核心意义。

## 13. 后续改进

如果继续优化我的部分，可以做几个方向。

第一，加入 VAD，只识别人声片段，减少无效推理。

第二，优化 whisper.cpp Android 编译参数，比如线程数、ARM NEON 和量化 kernel。

第三，加入流式识别，让用户边说边看到结果。

第四，增加英文和法语测试，验证多语言表现。

第五，做更标准的 CER 或 WER 质量评估。
