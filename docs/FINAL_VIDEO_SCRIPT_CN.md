# ASR-Mobile 项目视频文稿

## 0. 开场

大家好，我们这次介绍的项目是 ASR-Mobile，一个面向 Android 手机的离线语音识别部署项目。

这个项目不是单纯做模型压缩，也不是只在电脑上跑一个语音识别 demo，而是希望把 ASR 模型真正部署到手机端，实现本地录音、本地模型加载、本地 whisper.cpp 推理，并通过真实 benchmark 数据评估移动端部署效果。

我们的核心问题是：

```text
小型或量化后的 ASR 模型，能不能在 Android 手机上离线运行？
如果能运行，它在模型大小、推理速度、内存占用和识别质量之间有什么取舍？
```

## 1. 项目目标

ASR-Mobile 的完整系统链路是：

```text
Android UI -> 录音 -> WAV 文件 -> Kotlin WhisperEngine -> JNI -> whisper.cpp -> 转写结果与性能指标
```

也就是说，用户在手机 App 上录音后，音频会保存为本地 WAV 文件，然后由 Kotlin 层调用 WhisperEngine，再通过 JNI 调用底层 whisper.cpp 后端，最后返回识别文本和性能指标。

我们希望证明三件事：

第一，Android 手机可以完成本地离线 ASR，不依赖云端服务器。

第二，不同模型和量化等级会明显影响模型大小、加载时间、推理速度和识别质量。

第三，移动端部署不能只看理论模型大小，必须用真实手机测试，因为实际性能会受到 Android 后端、CPU、量化 kernel 和设备调度影响。

## 2. 分工说明

我们这部分主要围绕“量化、压缩和轻量化架构”展开。

两个人的分工是：

A 负责模型与量化部分，包括整理 tiny 和 base 模型、准备 Q8、Q5、Q4 量化模型、分析模型大小变化，并解释量化、压缩、剪枝和蒸馏的理论基础。

B 负责 Android Benchmark 与系统实验部分，包括运行 Android App、完善 benchmark 指标、进行真机测试、导出 CSV 数据，并分析模型在手机端的实际部署效果。

这两个方向共同服务于整个 Git 项目的核心目标，也就是 Android 端离线 ASR 部署与评测。

## 3. Android App 实现

在 Android 端，我们实现了几个核心功能。

第一是录音功能。用户可以在 App 中点击录音按钮，录制 10 秒音频，并保存为本地 `latest.wav`。

第二是模型加载功能。App 支持加载内置模型，也支持选择外部 `.bin` 模型文件。模型加载后，会记录模型加载时间。

第三是转写功能。App 会调用 whisper.cpp 后端，对本地 WAV 文件进行离线语音识别。

第四是 benchmark 功能。我们扩展了 benchmark 字段，包括：

- 设备型号
- Android 版本
- CPU ABI
- 模型名称
- 量化等级
- 音频语言
- 模型大小
- 加载时间
- 推理时间
- RTF
- Java heap 变化
- native heap 变化
- 转写文本
- 质量评分和备注字段

其中 RTF，也就是 real-time factor，等于推理时间除以音频时长。如果 RTF 小于 1，说明模型推理速度快于实时；如果 RTF 大于 1，说明转写比音频播放本身更慢。

我们还给 App 增加了进度条、进度文字和实验摘要区域，使实验过程更直观。

## 4. 自动化实验支持

为了避免手动一个一个选择模型，我们还加入了 ADB 自动化入口。

现在可以通过命令指定模型路径、模型名称、音频语言，并让 App 自动加载模型、自动运行 benchmark。

同时我们写了三个脚本：

```text
sync_day4_models_to_device.sh
run_day4_benchmark_matrix.sh
summarize_day4_benchmarks.py
```

第一个脚本负责把模型同步到手机 App 私有目录。

第二个脚本负责批量运行 Day 4 benchmark。

第三个脚本负责把多个 CSV 文件合并，并计算每个模型的平均推理时间、平均 RTF 和内存变化。

这样做的好处是实验更可复现，也减少了人工抄写错误。

## 5. 模型矩阵

我们测试和验证的模型主要包括 tiny 和 base 两个规模，以及 Q8、Q5、Q4 等量化等级。

主要模型包括：

```text
ggml-tiny.bin
ggml-tiny-q8_0.bin
ggml-tiny-q5_1.bin
ggml-tiny-q4_0.bin
ggml-base.bin
ggml-base-q8_0.bin
ggml-base-q5_1.bin
ggml-base-q4_0.bin
```

其中 tiny 模型更适合移动端实时部署，base 模型理论上识别质量更好，但模型更大、推理成本更高。

Q8 是轻度量化，通常希望在较小质量损失下减小模型。

Q5 是中度量化，希望在体积、速度和质量之间取得折中。

Q4 是更激进的量化，模型更小，但质量和运行稳定性风险更大。

## 6. 量化和压缩原理

量化的核心思想是降低模型权重的表示精度。

原始模型可能使用 16 位或 32 位浮点数表示权重，而量化模型会用更低 bit 的整数或特殊格式来表示权重。

这样做的直接好处是模型文件变小，内存占用可能降低，理论上计算压力也可能减少。

但是量化也会带来误差。因为低精度表示无法完全保留原始权重信息，所以可能导致识别质量下降。

更重要的是，量化不一定总是带来速度提升。是否加速取决于底层推理后端是否对这种量化格式做了高效实现，以及手机 CPU 是否适合这种计算方式。

这也是我们这次实验最重要的发现之一。

## 7. 实验设备和方法

我们的正式测试设备是华为手机：

```text
Device: HUAWEI HBN-AL10
Android: 12
ABI: arm64-v8a
```

正式中文测试音频长度为 10 秒。

测试句子是：

```text
这是 ASR Mobile 项目的第四天正式测试。我们正在比较不同量化模型在华为手机上的离线语音识别速度和识别质量。
```

每个模型重复测试 3 次，然后计算平均推理时间和平均 RTF。

我们主要比较：

- 模型大小
- 加载时间
- 推理时间
- RTF
- 识别文本质量
- 是否能够稳定完成测试

## 8. 实验结果

正式中文 benchmark 的结果如下。

`ggml-tiny.bin` 模型大小是 74.09 MB，平均推理时间是 8226.67 ms，平均 RTF 是 0.822。

这说明它在这台手机上能够快于实时完成转写，是最实用的模型。

`ggml-tiny-q8_0.bin` 模型大小下降到 41.52 MB，相比 tiny baseline 减少了大约 43.96%。但是它的平均推理时间变成了 40064.67 ms，平均 RTF 是 4.006。

也就是说，虽然模型变小了，但实际推理速度明显变慢。

`ggml-tiny-q5_1.bin` 模型大小进一步下降到 30.66 MB，相比 baseline 减少了大约 58.62%。但是它的平均推理时间达到 108814.67 ms，平均 RTF 是 10.882。

`ggml-base-q8_0.bin` 模型大小是 77.98 MB，平均推理时间是 111234.33 ms，平均 RTF 是 11.123。它能完成测试，但不适合当前实时移动端部署。

`ggml-base-q5_1.bin` 虽然在 Day 2 能够成功加载，但在正式 benchmark 中超时。

## 9. 结果分析

从模型大小来看，量化确实有效。

tiny Q8 从 74.09 MB 降到 41.52 MB，tiny Q5 降到 30.66 MB。

这说明量化确实可以显著降低模型存储体积。

但是从推理速度来看，结果和理论预期不完全一致。

在我们的 Android whisper.cpp 后端上，量化模型并没有变快，反而明显变慢。

这说明移动端部署不能只看模型大小，也不能简单认为量化一定加速。

真正影响部署效果的因素包括：

- whisper.cpp 对量化格式的 kernel 支持
- ARM CPU 对低精度计算的支持
- 线程调度
- 内存访问开销
- 手机系统运行状态
- 模型格式和后端实现细节

因此，量化是一种有效的压缩方法，但它是否适合最终部署，必须通过真机 benchmark 来判断。

## 10. 识别质量分析

从识别文本来看，各个成功模型都能识别出句子的大致内容，但都有一些明显错误。

例如 `ASR Mobile` 有时会被识别成相近但错误的文本，`语音识别` 也会出现错字。

我们基于参考文本和转写文本做了一个简单的字符错误率估算。

结果显示，tiny baseline 和 tiny Q8 的估算质量分数都在 4/5 左右，说明文本大意可用，但仍然存在明显字符级错误。

base Q8 在部分内容上看起来更标准，但推理时间太长，因此不适合作为当前部署模型。

## 11. 最终推荐模型

综合模型大小、推理速度、RTF 和识别可用性，我们最终推荐：

```text
ggml-tiny.bin
```

推荐理由有四点。

第一，它的模型大小是 74.09 MB，在手机本地部署中可以接受。

第二，它的平均 RTF 是 0.822，是本次正式测试中唯一快于实时的模型。

第三，它的识别文本虽然有错误，但整体语义可用。

第四，它比量化模型更稳定，更适合作为当前 Android App 的默认部署模型。

## 12. 项目结论

本项目最终得出的结论是：

```text
量化可以显著减小模型体积，但在当前 Android whisper.cpp 后端上，并没有带来速度提升。
```

所以，移动端 ASR 部署不能只依赖理论分析，必须做真实设备测试。

我们的实验表明，当前最适合 ASR-Mobile 的模型不是最小的模型，而是在大小、速度和识别效果之间最平衡的 `ggml-tiny.bin`。

这也体现了课程中模型压缩和端侧部署的核心思想：优化目标不是单一指标，而是多指标 trade-off。

## 13. 局限性

目前项目还有一些局限。

第一，正式 benchmark 只覆盖了一台华为手机。

第二，正式测试主要是中文音频，没有完成英文和法语正式实验。

第三，识别质量目前主要基于文本检查和简单字符错误率估算，还没有做完整标准化 CER 或 WER 评估。

第四，当前还没有实现流式识别，仍然是录音完成后再整体转写。

第五，量化模型速度较慢的问题还没有深入到 native kernel 层面做优化。

## 14. 后续优化方向

后续可以从几个方向继续优化。

第一，加入 VAD，也就是语音活动检测，只把有人声的片段送入 ASR 模型，减少无效推理。

第二，优化 whisper.cpp 的 Android 编译参数，例如线程数、ARM NEON、FP16 或量化 kernel 支持。

第三，加入简单后处理，对常见错词进行修正，比如把错误识别的 `AS2` 或 `AIS2` 修正为 `ASR`。

第四，增加英文和法语测试，验证多语言场景下模型表现是否一致。

第五，尝试流式 ASR，让用户可以边说边看到识别结果，而不是等待整段音频处理完。

## 15. 结束语

总的来说，ASR-Mobile 完成了一个从 Android 录音、模型加载、whisper.cpp 本地推理，到 benchmark 数据导出的完整离线 ASR 部署链路。

我们不仅验证了模型可以在手机端运行，也通过真实数据分析了量化压缩在移动端的收益和代价。

最终结论是：在当前设备和后端条件下，`ggml-tiny.bin` 是最适合部署的模型，而量化模型更适合作为压缩 trade-off 的实验对照。
